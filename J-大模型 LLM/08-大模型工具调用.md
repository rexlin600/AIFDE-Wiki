# 大模型工具调用

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

LLM 只能生成 Token，不能仅凭文字可靠地查询实时订单、发送邮件或退款。工具调用让模型提出结构化动作，由程序校验、授权和执行，再把结果回填给模型或用户。

关键边界是：模型拥有提议权，不拥有执行权。模型生成的工具名、参数、理由和“用户已同意”都属于不可信输入。

## 不理解会造成什么错误

- 模型一输出调用就直接执行，绕过身份与权限策略。
- 对有副作用的操作盲目重试，重复扣款、退款或发信。
- 超时后认定执行失败，实际远端已经成功，造成重复动作。
- 工具返回文本含恶意指令，下一轮模型照做。
- 把多步 Agent 循环塞进一次调用，没有步数、成本和终止边界。

## 它在 LLM 链路中的位置

```text
用户请求 → 模型提出工具调用 → 语法与参数校验 → 身份授权
→ 风险确认 → 幂等执行 → 记录结果 → 结果回填 → 生成答复
                       └→ 拒绝、超时查询、补偿或人工处理
```

单次工具接口在本篇讲清；多步规划、记忆和循环控制属于 [Agent](../L-%E6%99%BA%E8%83%BD%E4%BD%93%20Agent/00-%E6%99%BA%E8%83%BD%E4%BD%93%20Agent-MOC.md)。

## 从订单退款开始

用户请求退还订单 A102 的 30 元运费。模型可提出 `refund(order_id="A102", amount=30)`，程序仍需验证：

- 参数满足 Schema 和金额范围；
- 当前登录用户拥有 A102；
- 订单符合退款政策；
- 高风险条件是否需要再次确认；
- 本次业务请求是否已经执行过。

工具返回的是数据库事实；模型不得把自己之前生成的订单信息当作授权证据。

## 先建立简单基线

低频高风险操作先使用普通表单和确定性工作流，让模型只帮助解释或预填字段。只有自然语言入口明显改善完成率且控制措施充分时，才开放工具提议。

## 工具状态机

```text
PROPOSED
→ VALIDATED
→ AUTHORIZED
→ CONFIRMED
→ EXECUTING
→ SUCCEEDED
```

任一步都可能进入 `REJECTED`。执行超时应进入 `UNKNOWN`，先用幂等键查询既有结果，不能立即假定失败并重做。可安全重试的只读调用也要限制次数、退避和总时限。

## 幂等性怎样阻止重复副作用

为一次业务意图生成稳定幂等键 $k$。执行层保存映射：

$$
k\rightarrow(status,result)
$$

第一次成功后，相同键再次到达就返回已有结果，不再次改变余额。幂等键应绑定用户、动作和业务对象，不能只用随机的“本次网络请求 ID”，否则客户端重试会产生新键。

设单次调用在返回前超时概率为 $q$。若超时后无条件重试一次，而第一次其实已成功，则重复副作用风险可接近 $q$；使用正确幂等键后，两次请求仍对应一个业务动作。

## 最小手算

用户余额 100 元，退款 30 元。第一次远端成功后余额变为 130，但响应丢失。如果重试再次执行，余额错误地变成 160；若两次使用同一幂等键，第二次返回第一次结果，余额保持 130。

工具最大 3 次，每次超时 2 秒，退避 0.5 秒和 1 秒，则仅工具阶段最坏约为 $3\times2+0.5+1=7.5$ 秒，还未包括模型生成。用户可接受延迟低于此值时必须降低次数或改异步。

## 可执行实验

下面用内存账本模拟“校验、授权、幂等执行”。成功退款、越权请求和重复请求都有断言。

```python
import random
import re

random.seed(42)

class RefundService:
    def __init__(self):
        self.orders = {"A102": {"owner": "u1", "paid": 80, "refunded": 0}}
        self.results = {}

    def execute(self, proposal, actor, idempotency_key):
        required = {"tool", "order_id", "amount"}
        if set(proposal) != required or proposal["tool"] != "refund":
            raise ValueError("invalid tool schema")
        if not re.fullmatch(r"A\d{3}", proposal["order_id"]):
            raise ValueError("invalid order id")
        amount = proposal["amount"]
        if isinstance(amount, bool) or not isinstance(amount, int) or amount <= 0:
            raise ValueError("invalid amount")
        if idempotency_key in self.results:
            return self.results[idempotency_key]
        order = self.orders.get(proposal["order_id"])
        if order is None or order["owner"] != actor:
            raise PermissionError("actor cannot refund this order")
        if order["refunded"] + amount > order["paid"]:
            raise ValueError("refund exceeds paid amount")
        order["refunded"] += amount
        result = {"status": "succeeded", "refunded": amount}
        self.results[idempotency_key] = result
        return result

service = RefundService()
proposal = {"tool": "refund", "order_id": "A102", "amount": 30}
first = service.execute(proposal, actor="u1", idempotency_key="u1:A102:shipping")
replayed = service.execute(proposal, actor="u1", idempotency_key="u1:A102:shipping")
assert first == replayed
assert service.orders["A102"]["refunded"] == 30  # 没有重复退款

try:
    service.execute(proposal, actor="attacker", idempotency_key="attacker:A102:x")
    raise AssertionError("unauthorized request should fail")
except PermissionError:
    pass

try:
    service.execute({**proposal, "amount": 100}, "u1", "u1:A102:too-much")
    raise AssertionError("out-of-range business request should fail")
except ValueError:
    pass

print(first, service.orders["A102"], "failure branches passed")
```

## 实验结果解释

第一次和重放得到同一结果，且累计退款保持 30，证明幂等层阻止重复副作用。越权和超额退款在执行前被拒绝。实验是单进程内存模拟；真实服务需用数据库唯一约束或事务保证并发原子性。

## 质量延迟与成本影响

- 工具能提供实时事实和确定性计算，但增加网络、排队和回填 Token。
- 并行只适用于彼此独立的只读调用；有依赖和副作用的步骤必须按状态推进。
- 超时预算应覆盖模型、工具和重试总链路，不能各组件分别用完整 SLA。
- 缓存只读结果要定义用户隔离和新鲜度；有副作用结果用幂等记录，不用普通响应缓存替代事务。

## 数据评测与安全风险

评测不只看工具名准确率，还要看参数准确率、校验拒绝率、越权阻断、重复执行、超时恢复和最终任务成功率。使用沙箱与测试账户注入恶意用户文本和恶意工具返回值。

工具只授予完成任务所需最小权限。密钥不进入 Prompt，调用凭证由执行层持有。高风险动作需要明确用户确认、金额限制、审计日志和必要的人工审批。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 模型选错工具 | 描述重叠或任务不可判定 | 混淆集、工具边界、拒绝选项 |
| 参数格式正确但执行失败 | 缺少业务校验 | 实体存在性、所有权、状态前置条件 |
| 出现重复扣款或退款 | 重试无稳定幂等键 | 业务意图键、唯一约束、超时路径 |
| 工具超时后状态不明 | 把超时当失败 | 按幂等键查询、UNKNOWN 状态、对账 |
| 工具结果诱导下一动作 | 返回内容不可信 | 结果标记、允许工具集合、重新授权 |
| 循环不停止 | 无步数和预算上限 | 状态机、终止条件、总 Token 与时间 |

## 适用与不适用场景

工具调用适合实时查询、精确计算和受控外部动作。纯知识解释无需强行调用工具；不可逆、高金额或生命安全操作不应由模型单独决定。复杂多步执行需要 Agent 层的计划、状态和人工接管。

## 学习收益

你应能把工具调用设计成“提议、校验、授权、确认、幂等执行、回填”的状态机，解释超时为何不是失败，并为副作用操作设计可审计恢复。

## 给别人讲清楚

“模型像会写申请单的助理：它能建议调用什么、填哪些参数，但门禁核验身份，业务系统审批，执行层保证同一申请不会办两次。”
