# 大模型从头预训练

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

从头预训练让组织自行决定 Tokenizer、数据混合、模型架构、参数量和许可边界。它适合现有基础模型无法覆盖的语言、数据主权、部署许可或研究目标，不是获得“专属知识”的默认办法。

多数业务知识更新更适合检索增强，行为和格式适配更适合 SFT 或 LoRA。从头训练要同时建立数据、分布式训练、评测、安全和长期运维能力，远不止启动一次训练脚本。

## 不理解会造成什么错误

- 把训练损失下降当成模型已经具备可用语言能力。
- 只估算权重显存，漏掉梯度、优化器状态、激活和检查点。
- 先确定参数量，再发现高质量 Token 不够或计算预算不足。
- 测试集进入去重、Tokenizer 训练或预训练数据，污染结果。
- 训练中断后只有权重，没有优化器、数据位置和随机状态。

## 它在 LLM 链路中的位置

流程是需求与基线 → 数据治理 → Tokenizer → 小规模试跑 → 模型与预算 → 分布式训练 → 检查点 → 基础能力评测 → SFT 与偏好对齐 → 服务。任何后期训练都无法可靠补救严重的数据许可、隐私和评测污染问题。

## 先回答是否真的需要

至少比较四条基线：直接使用现有模型、Prompt 与上下文工程、RAG、继续预训练或微调。只有当语言覆盖、控制权、规模或许可证要求无法由这些方案满足，而且收益能覆盖持续训练与维护成本时，才进入从头预训练。

## 数据流水线

数据不是一个文本文件夹，而是可追踪的版本化系统：来源登记、许可与用途、个人信息处理、质量过滤、语言识别、文档级与近似去重、测试集隔离、切分、Token 化和混合采样。每个训练样本应能追溯到数据版本和处理规则。

混合比例决定模型“练习什么”。若领域 $i$ 有 $D_i$ 个 Token、采样权重为 $w_i$，可用：

$$
p_i=\frac{w_iD_i}{\sum_j w_jD_j}
$$

提高 $w_i$ 会增加该领域出现频率，但可能挤压其他能力。比例必须通过分域验证集而非直觉选择。

## 计算预算的粗估

对标准稠密自回归 Transformer，一个常用数量级估算是：

$$
C\approx6ND
$$

$N$ 是非 Embedding 参数量，$D$ 是训练 Token 数，$C$ 是训练浮点运算次数。系数 6 来自前向与反向的粗略合计；架构、序列长度、重计算、稀疏性和硬件利用率都会改变真实成本，所以它只能用于早期量级判断。

若持续计算能力为 $F$ FLOP/s、有效利用率为 $u$，理想训练秒数近似：

$$
t\approx\frac{C}{Fu}
$$

## 最小手算

一个 10 亿参数模型训练 200 亿 Token，$C\approx6\times10^9\times2\times10^{10}=1.2\times10^{20}$ FLOP。若集群持续提供 $10^{15}$ FLOP/s，利用率 0.4，理想时间约 $3\times10^5$ 秒，即 3.47 天。它未计故障、评测、保存和试验返工。

## 可执行实验

```python
def estimate(parameters, tokens, sustained_flops, utilization):
    training_flops = 6 * parameters * tokens
    seconds = training_flops / (sustained_flops * utilization)
    return training_flops, seconds / 86400

flops, days = estimate(
    parameters=1_000_000_000,
    tokens=20_000_000_000,
    sustained_flops=1_000_000_000_000_000,
    utilization=0.4,
)
print("training FLOPs", f"{flops:.2e}", "ideal days", round(days, 2))

checkpoint = {
    "model_step": 12000,
    "optimizer_step": 12000,
    "data_shard": 87,
    "sample_offset": 4200,
    "scheduler_step": 12000,
    "rng_seed": 20260910,
}
required = {"model_step", "optimizer_step", "data_shard",
            "sample_offset", "scheduler_step", "rng_seed"}
assert required <= checkpoint.keys()
assert checkpoint["model_step"] == checkpoint["optimizer_step"]
```

实验把预算变成可审查数字，也说明可恢复检查点必须包含训练状态和数据进度。真实系统还要保存各设备随机状态、梯度缩放器和配置哈希。

## 从小规模试跑到正式训练

先做单批过拟合，验证输入与标签；再做小模型和短训练，验证损失曲线、吞吐、检查点恢复与分域评测；最后才扩大规模。扩容前要演练节点故障、坏样本跳过和回滚。训练中持续查看总体损失、分域损失、梯度范数、学习率、有效 Token/s、硬件利用率和数据吞吐。

## 检查点为何不仅是权重

仅加载权重再训练会丢失动量、学习率进度、数据位置与随机序列，导致轨迹突变或样本重复。完整恢复应保存模型、优化器、调度器、随机状态、数据游标、混合配置和代码版本，并通过“中断后续跑与不中断对照”验证。

## 结果怎样解释

训练损失降低只说明模型更会预测训练分布。验收需要独立且去污染的语言、知识、推理、代码、安全和目标领域评测；按模型尺寸与训练 Token 画学习曲线；与更便宜的现有模型、RAG 和微调基线比较。单个公开榜单不能证明业务价值。

## 质量延迟与成本影响

更大模型增加训练、推理、存储和迭代成本；更多 Token 延长训练并可能收益递减。序列长度会显著影响激活和 Attention。预算至少包含数据处理、试跑、正式训练、失败重跑、评测、后训练和长期推理，而不是只算一次 GPU 租用。

## 数据评测与安全风险

建立数据卡、模型卡、删除请求流程和事件响应。预训练语料可能含个人信息、恶意代码、偏见与受限内容。测试集在建库前即应登记指纹并排除近重复；安全评测应按语言和领域分层。任何无法追溯的数据都可能变成日后的合规债务。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 首批损失不接近随机基线 | 标签错位或词表配置错误 | 单批样本、shift、词表大小 |
| 损失下降但验证不改善 | 重复、过拟合或分布错配 | 去重、分域验证、数据混合 |
| 恢复后损失跳变 | 状态或数据游标缺失 | 优化器、调度器、随机状态 |
| Token 吞吐突然下降 | 数据或通信瓶颈 | 加载时间、设备利用率、网络 |
| 榜单异常优秀 | 训练测试污染 | 文本与语义近重复、时间切分 |
| 预算持续超支 | 利用率假设过高或频繁重跑 | 实测 MFU、故障率、检查点间隔 |

## 适用与不适用场景

适用于确有独特语言、许可、架构或主权需求，并拥有长期数据与计算能力的团队。不适用于只想注入少量企业知识、改善输出格式或快速验证产品的场景；这些通常先考虑 RAG、SFT 或 LoRA。

## 学习收益

你应能画出从数据到后训练的完整流程，用 $6ND$ 做量级估算，说明检查点的完整状态，并设计避免污染的多维评测。

## 给别人讲清楚

“从头预训练不是把文本倒进 GPU，而是从数据许可、词表、预算到恢复和评测的一整套工厂。训练损失下降只说明机器运转了，不说明产品已经合格。”
