# 大模型结构化输出

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

聊天文本适合人读，业务程序需要稳定字段。结构化输出把模型结果变成可解析、可校验、可重试和可降级的数据契约，用于工单分类、信息抽取、审核建议和工具参数生成。

## 不理解会造成什么错误

- JSON 能解析就直接入库，忽略类型、范围和业务含义。
- 用正则从任意自然语言里“捞字段”，产生静默错配。
- 解析失败后无限重试，放大成本和延迟。
- 自动修复所有错误，把模型原本不确定的值改造成看似合法的数据。
- Schema 升级没有版本，消费者对同一字段产生不同解释。

## 它在 LLM 链路中的位置

```text
Prompt 与上下文 → 模型文本
→ 语法解析 → Schema 校验 → 语义校验 → 业务校验
→ 接受 | 有限修复 | 有限重试 | 降级人工
```

结构化输出只负责把候选结果变成受控数据，不代表内容为真，更不代表获准执行。涉及外部动作时还要经过[大模型工具调用](08-大模型工具调用.md)的授权层。

## 从客服工单抽取开始

模型需要输出：

```json
{"order_id":"A102","issue":"delivery","urgency":2}
```

- `order_id` 应符合业务格式；
- `issue` 只能是允许枚举；
- `urgency` 必须是 1 到 3 的整数；
- 缺证据时字段应为 `null` 或进入人工流程，而不是编造。

## 先建立简单基线

若只抽取格式固定的订单号，先比较正则和规则。LLM 适合语义变化较大的字段，但仍必须由确定性代码验证。基线应报告字段级准确率和整条记录通过率。

## 四层正确性

1. **语法正确：** 字符串是不是合法 JSON。
2. **结构正确：** 必需字段、类型和额外字段是否符合 Schema。
3. **语义正确：** 枚举、范围、格式和字段间约束是否成立。
4. **事实与业务正确：** 订单是否存在、是否属于当前用户、动作是否允许。

语法约束生成或 JSON Schema 可以改善前两层，不能自动保证后两层。例如 `{"urgency":2}` 语法完全正确，但模型可能错误理解了用户的紧急程度。

## 状态推导

把单次处理写成有限状态机：

```text
RAW → PARSED → SCHEMA_VALID → SEMANTIC_VALID → ACCEPTED
  └→ PARSE_ERROR ─┐
       SCHEMA_ERROR├→ RETRY，达到上限后 → DEGRADED
     SEMANTIC_ERROR┘
```

设单次成功率为 $p$，各次失败近似独立，最多尝试 $K$ 次，则至少一次成功概率为：

$$
P_{success}=1-(1-p)^K
$$

但真实错误往往相关：同一输入重复调用可能重复犯错。重试不是免费的正确性来源，必须限制次数并改变反馈或降级策略。

## 最小手算

若单次成功率 $p=0.8$，最多两次，理想独立假设下成功率是 $1-0.2^2=0.96$。若每次平均花 500 ms，20% 请求进入第二次，则平均模型时间约 $500+0.2\times500=600$ ms，还没计算排队和校验。

假设 100 条记录中 90 条每个字段都正确，另 10 条各错一个字段。若每条 3 个字段，字段准确率是 $290/300=96.7\%$，整条通过率却只有 90%。接口可靠性通常更关心整条记录。

## 可执行实验

下面使用标准库区分解析、结构和语义错误。有限修复只移除明确的 Markdown 代码围栏，不猜测字段值。

```python
import json
import random
import re

random.seed(42)
ALLOWED_ISSUES = {"delivery", "refund", "product"}

def strip_json_fence(text):
    match = re.fullmatch(r"\s*```(?:json)?\s*(.*?)\s*```\s*", text, re.S)
    return match.group(1) if match else text

def validate_output(text):
    try:
        value = json.loads(strip_json_fence(text))
    except json.JSONDecodeError as error:
        raise ValueError("syntax_error") from error
    if not isinstance(value, dict):
        raise ValueError("schema_error:not_object")
    required = {"order_id", "issue", "urgency"}
    if set(value) != required:
        raise ValueError("schema_error:fields")
    if not isinstance(value["order_id"], str):
        raise ValueError("schema_error:order_id_type")
    if not isinstance(value["urgency"], int) or isinstance(value["urgency"], bool):
        raise ValueError("schema_error:urgency_type")
    if not re.fullmatch(r"A\d{3}", value["order_id"]):
        raise ValueError("semantic_error:order_id")
    if value["issue"] not in ALLOWED_ISSUES:
        raise ValueError("semantic_error:issue")
    if not 1 <= value["urgency"] <= 3:
        raise ValueError("semantic_error:urgency")
    return value

valid = validate_output(
    '```json\n{"order_id":"A102","issue":"delivery","urgency":2}\n```'
)
assert valid["order_id"] == "A102"

failures = {
    '{"order_id":': "syntax_error",
    '{"order_id":"A102","issue":"delivery"}': "schema_error",
    '{"order_id":"A102","issue":"delivery","urgency":9}': "semantic_error",
}
for candidate, expected in failures.items():
    try:
        validate_output(candidate)
        raise AssertionError("invalid candidate should fail")
    except ValueError as error:
        assert str(error).startswith(expected)

print(valid, "all failure layers detected")
```

## 实验结果解释

成功断言证明围栏内合法对象可进入语义层；三个失败断言分别定位语法、缺字段和范围错误。实验没有核验订单是否真实存在或属于当前用户，那是业务系统责任。

## 质量延迟与成本影响

- 结构约束可减少解析失败，但更复杂 Schema 可能提高生成难度。
- 重试应记录原因、次数和额外 Token；超过上限转人工或返回明确错误。
- 只返回需要字段能减少输出 Token 和解析歧义。
- 供应商的约束解码能力不同，应在目标模型和实际 Schema 上测整条通过率。

## 数据评测与安全风险

模型输出永远是不可信输入。字符串可能含脚本、路径或 SQL，数值可能越界，URL 可能指向内部网络。进入数据库、模板、Shell 或工具前要按目标环境编码和验证。

评测至少区分解析率、Schema 通过率、字段准确率、整条准确率和业务校验通过率。只报告 JSON 可解析率会严重夸大系统质量。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| JSON 偶尔无法解析 | 输出混入说明或被截断 | 停止原因、输出预留、原始响应 |
| Schema 通过但字段错 | 只做语法结构约束 | 标注集、语义规则、事实核验 |
| 重试造成延迟尖峰 | 上限过高或错误相关 | 失败类型、重试收益、降级比例 |
| Schema 升级后消费者失败 | 无版本或兼容策略 | schema_version、契约测试 |
| 自动修复产生假数据 | 修复范围过宽 | 修复日志、原始值、人工降级 |
| 输出引发注入 | 未按不可信输入处理 | 参数化接口、编码、允许列表 |

## 适用与不适用场景

结构化输出适合模型结果要进入程序流程的任务。开放式创作不必强制复杂 Schema；高风险财务、医疗或权限操作即使格式正确也不能自动执行，必须进行事实、权限和人工控制。

## 学习收益

你应能区分语法、结构、语义和业务正确性，设计有限状态与重试上限，并用分层指标说明接口究竟可靠到哪一步。

## 给别人讲清楚

“合法 JSON 只像字写得工整，不代表内容真实。先看能不能读，再看字段对不对、含义对不对，最后才问业务允不允许。”
