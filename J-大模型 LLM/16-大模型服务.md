# 大模型服务

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

大模型服务把离线模型变成可供多人稳定调用的系统。它不仅要“生成答案”，还要处理排队、动态批处理、流式返回、取消、超时、限流、版本切换和故障隔离。

聊天用户在意多快看到第一个字，批量摘要任务更在意每分钟完成多少 Token。服务设计必须先明确服务等级目标，而不是只报告单次 GPU 推理时间。

## 不理解会造成什么错误

- 用吞吐提升掩盖单个用户等待时间恶化。
- 把首 Token 延迟和完整响应延迟混成一个平均值。
- 无限增大批量，导致排队、显存和超时失控。
- 客户端断开后仍继续生成，浪费算力。
- 重试非幂等请求，造成重复扣费或重复写入。

## 它在 LLM 链路中的位置

服务位于模型、量化和 KV Cache 之后，位于应用 API 之前。请求经过鉴权与限流，进入调度队列；引擎执行 Prefill 与 Decode，逐步流式返回 Token，同时采集模型版本、提示长度、完成长度和延迟指标。

## 四个核心指标

设请求到达时间为 $t_0$，首 Token 返回为 $t_1$，最后一个 Token 返回为 $t_n$：

$$
\mathrm{TTFT}=t_1-t_0,\qquad
\mathrm{E2E}=t_n-t_0
$$

若共生成 $n$ 个 Token，首 Token 之后的平均间隔为：

$$
\mathrm{ITL}=\frac{t_n-t_1}{n-1}\quad(n>1)
$$

吞吐量是单位时间完成的请求数或 Token 数。TTFT 包含排队和 Prefill；ITL 主要反映 Decode 调度。只看 P50 会隐藏少数用户的长等待，因此还要报告 P95、P99。

## 排队为何会放大延迟

单个服务台的直觉是：利用率 $\rho$ 越接近 1，突发请求越难被吸收。一个简化的 M/M/1 模型给出平均系统时间：

$$
W=\frac{1}{\mu-\lambda}
$$

$\lambda$ 是平均到达率，$\mu$ 是平均服务率。若每秒能处理 10 个请求，流量从 5 增到 9，公式中的平均时间从 0.2 秒增到 1 秒。真实 LLM 请求长度差异很大，不满足该模型假设，但它揭示了“留余量”的必要性。

## 连续批处理怎样工作

静态批处理等待一批请求一起完成，短请求会被长请求拖住。连续批处理允许已完成请求离开，并在新的解码步加入其他请求。调度器每步都在吞吐、TTFT、公平性和显存之间权衡。

Prefill 一次处理整段输入，计算密集；Decode 每步只产生一个新 Token，频繁读取权重和 KV Cache。把二者分开观测，才能知道长提示和长回答分别造成什么压力。

## 最小手算

某请求在 0 ms 到达，100 ms 返回首 Token，之后 4 个 Token 分别在 140、180、220、260 ms 返回。TTFT 是 100 ms，E2E 是 260 ms，五个 Token 的平均 ITL 是 $(260-100)/(5-1)=40$ ms。

若只报告 E2E，无法判断用户慢在排队和 Prefill，还是慢在逐 Token 生成。

## 可执行实验

```python
from collections import deque

def simulate(jobs, capacity):
    """每个时间步最多为 capacity 个活跃请求各生成一个 Token。"""
    waiting = deque(sorted(jobs))  # (arrival, request_id, output_tokens)
    active, records, now = [], {}, 0
    while waiting or active:
        while waiting and waiting[0][0] <= now:
            arrival, request_id, tokens = waiting.popleft()
            active.append([arrival, request_id, tokens])
        if not active:
            now = waiting[0][0]
            continue
        for job in active[:capacity]:
            arrival, request_id, left = job
            records.setdefault(request_id, {"arrival": arrival, "first": now + 1})
            job[2] = left - 1
            if job[2] == 0:
                records[request_id]["last"] = now + 1
        active = [job for job in active if job[2] > 0]
        now += 1
    return records

jobs = [(0, "long", 6), (1, "short", 2), (2, "medium", 3)]
serial = simulate(jobs, capacity=1)
batched = simulate(jobs, capacity=2)
for name, result in (("serial", serial), ("continuous", batched)):
    print(name, result)

assert batched["short"]["first"] < serial["short"]["first"]
assert batched["medium"]["last"] <= serial["medium"]["last"]
```

这个离散模型故意忽略 Prefill、批量效率和显存，只展示调度对等待时间的影响。生产结论必须由真实引擎压测得到。

## 请求状态与失败处理

一个请求至少经历 `received → queued → prefill → decoding → completed`。任何阶段都可能进入 `cancelled`、`timed_out` 或 `failed`。客户端取消后应传播取消信号并回收 KV Cache；超时必须有总时限和阶段时限；重试需区分只读生成与带外部副作用的工具调用。

## 实验结果怎样解释

示例中并发容量让短任务更早获得服务，但实际批量越大不一定越好。压测要使用接近生产的输入输出长度分布、到达突发和采样参数，并同时记录 P50/P95/P99 TTFT、ITL、E2E、Token 吞吐、错误率、显存峰值和取消回收时间。

## 质量延迟与成本影响

限制最大输出 Token 能直接控制尾延迟和费用，但可能截断答案。量化减少权重内存，KV Cache 管理提高并发，推测解码可能降低生成等待；每项优化都要检查输出质量。自动扩容要考虑模型加载时间，保留温热容量才能应对突发。

## 数据评测与安全风险

日志中可能包含提示、模型回答和个人信息。默认记录长度、哈希和结构化指标，正文采样要脱敏、限权和设保留期。网关负责鉴权、租户隔离、配额、输入大小和审计；模型服务不能把 Prompt 当作授权机制。灰度发布应可按请求追溯模型、Tokenizer、量化和模板版本。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| TTFT 高但 ITL 正常 | 排队或 Prefill 过慢 | 队列时间、输入长度、Prefill 批量 |
| TTFT 正常但输出很慢 | Decode 或缓存瓶颈 | ITL、KV 显存、每步批量 |
| 吞吐高但用户投诉 | 尾延迟或不公平调度 | P95/P99、长短请求切片 |
| 显存持续增长 | 取消后缓存未回收 | 请求状态、KV 生命周期 |
| 重试造成重复动作 | 工具请求非幂等 | 幂等键、状态存储、重试边界 |
| 扩容后仍超时 | 冷启动或上游限流 | 模型加载、健康检查、网关队列 |

## 适用与不适用场景

任何多用户或有稳定性要求的 LLM 应用都需要服务治理。个人离线实验可直接调用模型，但性能数字不能外推到并发生产环境。若主要延迟来自检索或工具，单独优化推理引擎不会解决端到端问题。

## 学习收益

你应能区分 TTFT、ITL、E2E 和吞吐，解释 Prefill、Decode 与连续批处理，设计请求状态机，并用真实流量分布做容量测试。

## 给别人讲清楚

“模型服务像餐厅：做一道菜快，不代表排队的人等得短。要分别测排队、第一口多久上、后续上菜速度和整桌完成时间，还要能取消、限流和回收座位。”

## 自检问题

1. 为什么更大的批量可能提高吞吐却恶化 TTFT？
2. 客户端断开后为什么必须尽快回收 KV Cache？
3. 为什么平均延迟不能替代 P95 和 P99？
