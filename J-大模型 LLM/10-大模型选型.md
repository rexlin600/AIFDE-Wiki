# 大模型选型

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

大模型选型是在真实约束下选择模型与部署方式，而不是挑公开榜单最高分。客服抽取看字段准确率和成本，代码助手看仓库理解与延迟，高风险问答还看依据、拒答、隐私和许可。

合理选型的产物应是可复现证据：固定任务集、评分规则、负载、版本、权重和淘汰条件。它也允许答案是“小模型处理多数请求，复杂请求升级到大模型”。

## 不理解会造成什么错误

- 用通用榜单替代自己的业务样本。
- 把上下文窗口、参数量或厂商宣传当成效果保证。
- 混用不同 Prompt、采样参数和工具配置做比较。
- 只看单价，遗漏输出长度、重试、并发和工程成本。
- 加权总分掩盖隐私、许可或安全的硬性不合格。

## 它在 LLM 链路中的位置

先定义业务任务与错误代价，再建立最小基线、候选模型、统一调用协议和离线评测；通过硬约束的候选进入压测、灰度和线上监控。Prompt、RAG、工具和量化配置都是候选系统的一部分，应与模型版本一起冻结。

## 先设硬门槛再加权

硬约束包括数据能否出域、许可证是否允许、语言与模态是否支持、最大延迟和最低安全指标。不满足即淘汰，不能用便宜或高质量分抵消。

对通过门槛的候选，将“越大越好”的指标归一化为：

$$
z_{ij}=\frac{x_{ij}-\min_j x_{ij}}{\max_j x_{ij}-\min_j x_{ij}}
$$

对延迟、成本等“越小越好”的指标反向处理。加权分数为：

$$
S_j=\sum_i w_i z_{ij},\qquad \sum_i w_i=1
$$

当某指标所有候选相同，归一化分母为零，应约定该指标不产生区分，而不是得到 NaN。

## 成本怎样算完整

单请求近似成本可以写为：

$$
C_{req}=T_{in}c_{in}+T_{out}c_{out}+C_{retrieval}+C_{tool}+C_{retry}
$$

自托管还应折算空闲容量、工程、监控和故障成本。平均值会掩盖长尾，应按输入输出长度分布估算 P50 和 P95 成本。

## 最小手算

候选 A 的质量、延迟、成本归一化收益为 `[0.9,0.4,0.3]`，候选 B 为 `[0.7,0.8,0.9]`。质量、延迟、成本权重 `[0.6,0.2,0.2]` 时，A 得 0.68，B 得 0.76；若质量权重提高为 0.8，另外两项各 0.1，则 A 得 0.79，B 得 0.73。结论依赖业务权重，所以必须做敏感性分析。

## 可执行实验

```python
models = {
    "A": {"quality": 0.90, "latency": 0.40, "cost": 0.30},
    "B": {"quality": 0.70, "latency": 0.80, "cost": 0.90},
}

def rank(weights):
    scores = {
        name: sum(weights[key] * values[key] for key in weights)
        for name, values in models.items()
    }
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)

balanced = rank({"quality": 0.6, "latency": 0.2, "cost": 0.2})
quality_first = rank({"quality": 0.8, "latency": 0.1, "cost": 0.1})
print("balanced", balanced)
print("quality first", quality_first)
assert balanced[0][0] == "B"
assert quality_first[0][0] == "A"
```

这里延迟和成本已提前转成“越大越好”的收益分。真实项目要保存原始单位和转换公式，防止漂亮的归一化表掩盖实际差距。

## 评测集怎样建立

从真实流量按意图、语言、长度、风险和工具类型分层采样；为关键失败补充挑战集；保留时间外测试集。每题定义自动或人工评分标准，并记录不可接受错误。先加入规则、检索或小模型基线，再比较大模型的增量价值。

生成任务的自动指标常不充分，应盲化人工评审并检查评审者一致性。结构化抽取可测字段级精确率和召回率；事实问答同时测可回答性、支持率和拒答；工具任务测参数、权限与最终状态。

## 延迟与容量测试

固定输入输出长度分布和并发到达过程，报告 TTFT、ITL、E2E、吞吐、错误率、显存和冷启动。托管 API 还要测速率限制、区域、数据保留和供应商故障；自托管要测量化、批处理、扩容和运维复杂度。

## 实验结果怎样解释

总分只是决策摘要，不是客观真理。展示原始指标、置信区间、硬门槛、权重和权重变化下的排名。如果两个模型差异落在评测噪声内，应优先选择更简单、便宜或可控的方案，而不是宣称微小领先。

## 质量延迟与成本影响

大模型通常能处理更复杂任务，但延迟和成本更高；小模型可以用路由、RAG 或工具弥补部分能力。级联策略先让便宜模型处理，低置信度再升级，但路由错误与二次调用也有代价。选型应以端到端系统为单位。

## 数据评测与安全风险

向外部模型发送数据前核对地域、保留、训练使用和删除条款。开源权重仍有许可证、供应链和运行安全问题。评测样本需要脱敏、权限控制和版本冻结；模型不能参与生成并评分同一套答案而没有人工校准。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 离线冠军线上变差 | 流量分布或链路不同 | 线上切片、Prompt、工具与采样 |
| 排名随权重剧烈变化 | 候选各有明显取舍 | 敏感性、硬门槛、业务代价 |
| 成本远高于估算 | 输出过长、重试或空闲容量 | Token 分布、重试率、利用率 |
| 同模型结果无法复现 | 版本或参数未冻结 | 模型 ID、模板、采样、日期 |
| 榜单好但任务差 | 基准错配或污染 | 真实评测集、时间切分 |
| 总分高却不能上线 | 硬约束被加权抵消 | 隐私、许可、安全门槛 |

## 适用与不适用场景

新建应用、模型升级、托管与自托管比较都需要选型流程。概念验证可以用小样本快速筛选，但不能把结果当上线结论。若需求和错误代价尚未定义，任何模型排名都没有稳定含义。

## 学习收益

你应能设计业务评测集，区分硬约束与加权偏好，计算完整成本，做权重敏感性分析，并制定灰度和回滚条件。

## 给别人讲清楚

“选模型像选运输方案：最快、最便宜、载重最大通常不是同一个。先排除不合法或不安全的，再用自己的货物和路线实测，最后说明权重变化会不会改变答案。”
