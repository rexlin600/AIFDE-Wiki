# 稀疏模型与长上下文

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

稀疏模型试图在不让每个 Token 激活全部参数的情况下扩大模型容量；长上下文方法试图让模型处理更长的历史、文档和代码。两者都在解决“规模扩展”，但前者扩参数容量，后者扩输入长度，不能混为一谈。

实际应用包括多语言专家模型、长合同审阅、代码仓库分析和长对话。宣称支持很长窗口，只说明接口能接收，不等于模型能稳定找到、组合和正确使用其中的信息。

## 不理解会造成什么错误

- 把总参数量当成每 Token 的实际计算量。
- 只看最大上下文窗口，不测信息处在不同位置时的准确率。
- MoE 路由集中到少数专家，造成过载和能力退化。
- 认为稀疏 Attention 自动保留所有关键依赖。
- 用塞满原文替代检索、证据排序和 Token 预算管理。

## 它在 LLM 链路中的位置

MoE 通常替换 Transformer 中的稠密前馈层；长上下文涉及位置表示、Attention 模式、训练长度和服务 KV Cache。应用侧的上下文工程负责选择内容，模型侧负责在给定窗口内计算，两者共同决定结果。

## MoE 如何只激活部分专家

设共有 $E$ 个专家，路由器为 Token 表示 $x$ 计算分数并取 top-k：

$$
g=\operatorname{softmax}(W_rx),\qquad
S=\operatorname{TopK}(g,k)
$$

输出只组合被选中的专家：

$$
y=\sum_{i\in S}\frac{g_i}{\sum_{j\in S}g_j}E_i(x)
$$

若 $E=8$、$k=2$，每个 Token 只运行两个专家的前馈计算；但所有专家权重仍需存储或跨设备通信。因此“激活参数少”不等于“部署内存少”。

## 负载均衡为何必要

若一个批次有 $N$ 个 Token，每个 Token 路由到 $k$ 个专家，则共有 $Nk$ 次专家分派。专家 $i$ 接收 $n_i$ 次，理想分派比例是 $1/E$。可用简单不均衡指标：

$$
I=\sum_{i=1}^{E}\left(\frac{n_i}{Nk}-\frac{1}{E}\right)^2
$$

完全均匀时 $I=0$。真实训练常加入辅助负载均衡损失和每专家容量；容量满后 Token 可能被丢弃或转给其他专家。均衡损失太强又会妨碍自然专业化。

## 长上下文的计算与能力

标准全 Attention 对长度 $T$ 需要约 $T^2$ 个 Token 对。长度从 4K 翻到 8K，Attention 对数约增为四倍。若每个 Token 只关注固定窗口 $w$，局部稀疏 Attention 约为 $Tw$，但窗口外信息必须通过全局 Token、分层结构或多层传播间接到达。

位置编码扩展、稀疏 Attention 和更大 KV Cache 解决的层面不同：能表示更远位置，不保证训练时见过这种长度；算得下，不保证找得到；找得到证据，也不保证推理正确。

## 最小手算

长度 $T=8$ 的因果全 Attention 有 $8\times9/2=36$ 个有效位置对。若每个 Token 最多看自身和前面 2 个位置，因果局部窗口的实际对数为 $1+2+3+3+3+3+3+3=21$，而不是简单的 $8\times3=24$，因为序列开头没有足够历史。底层若仍使用完整稠密矩阵，可能分配 $8^2=64$ 个位置。

四个专家收到 `[4, 4, 0, 0]` 个 Token 时，比例为 `[0.5,0.5,0,0]`，不均衡指标为 $4\times0.25^2=0.25$；均匀 `[2,2,2,2]` 时为 0。

## 可执行实验

```python
import numpy as np

routing_scores = np.array([
    [3.0, 2.0, 0.0, 0.0],
    [2.5, 2.0, 0.1, 0.0],
    [0.0, 0.0, 3.0, 2.0],
    [0.0, 0.0, 2.0, 3.0],
])
top_k = 2
selected = np.argpartition(routing_scores, -top_k, axis=1)[:, -top_k:]
loads = np.bincount(selected.ravel(), minlength=routing_scores.shape[1])
fractions = loads / loads.sum()
imbalance = np.sum((fractions - 1 / len(loads)) ** 2)
print("selected experts", selected.tolist())
print("loads", loads.tolist(), "imbalance", round(imbalance, 4))
assert loads.sum() == len(routing_scores) * top_k

def causal_pairs(length, window=None):
    return sum(min(position + 1, window or length) for position in range(length))

for length in (8, 16):
    print(length, "full", causal_pairs(length),
          "local window 3", causal_pairs(length, 3))
assert causal_pairs(8) == 36
assert causal_pairs(8, 3) == 21
```

因果全 Attention 只计算下三角时有 $T(T+1)/2$ 个有效对，底层稠密实现仍可能分配 $T^2$ 矩阵。实验中的路由刻意均衡，只证明计数逻辑，不代表专家已经学会不同能力。

## 怎样验证长上下文真的可用

建立位置分层测试：把唯一证据分别放在开头、中间、末尾，并改变干扰文档数量；同时测试精确检索、跨段组合、拒答和引用。报告输入长度与证据位置二维曲线，而不是只给一个平均分。再与“检索后只给相关片段”的短上下文基线比较质量、延迟和成本。

训练长度之外的位置外推必须单独验证。简单的 needle-in-a-haystack 能测找到字符串，却不能替代多证据推理、真实文档噪声和业务任务评测。

## 实验结果怎样解释

MoE 要同时报告总参数、每 Token 激活参数、路由分布、丢 Token 比例和通信占比。长上下文要同时报告最大可接受长度、不同位置的任务质量、TTFT、KV 显存和并发。任何单一数字都不足以描述能力。

## 质量延迟与成本影响

MoE 降低相同总容量下的每 Token 算术量，但专家并行会增加跨设备通信，负载不均会让最快设备等待最慢设备。长上下文增加 Prefill 时间和 KV Cache；即使采用稀疏 Attention，数据组织与检索仍有成本。更长窗口可能减少分块，却会放大噪声和提示注入面。

## 数据评测与安全风险

专家可能在语言、领域或敏感属性上形成难以审计的分工，应按路由和任务切片检查偏差。长上下文会引入更多不可信文本，系统指令、权限信息和检索内容必须分层，外部文档不能获得指令权限。测试语料需要避免将 needle 模板泄漏进训练数据。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 少数专家过载 | 路由塌缩或容量过小 | 路由直方图、容量因子、均衡损失 |
| 算力下降但延迟不降 | 专家通信成为瓶颈 | all-to-all 时间、专家放置、批量 |
| 长窗口能输入却答错 | 未在目标长度训练或利用不足 | 长度与证据位置切片 |
| 中间证据经常丢失 | 位置偏差或干扰过多 | 开中末对照、重排与分块 |
| 长请求导致 OOM | KV Cache 或 Attention 激增 | 上下文长度、并发、缓存 dtype |
| 稀疏 Attention 漏信息 | 关键依赖不在连接模式内 | 注意模式、全局 Token、检索基线 |

## 适用与不适用场景

MoE 适合希望扩大模型容量且具备高效专家并行基础设施的训练与推理平台。长上下文适合必须保留整体结构的长文档、代码和对话；若只有少量片段相关，RAG 往往更便宜、更易引用。小流量和单设备场景未必能获得 MoE 的系统收益。

## 学习收益

你应能区分总参数与激活参数，推导 top-k 专家组合和负载指标，比较 $T^2$ 与 $Tw$，并设计按证据位置分层的长上下文评测。

## 给别人讲清楚

“MoE 像让每道题只找少数专家，专家库很大但一次不全叫来；长上下文像给模型一张更大的桌子。桌子放得下更多材料，不代表它一定能找到中间那一页。”
