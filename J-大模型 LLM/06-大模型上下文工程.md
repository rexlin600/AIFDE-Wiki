# 大模型上下文工程

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 LLM 问题

上下文工程决定每次调用时让模型看到什么、按什么顺序看到、超出窗口时丢弃什么。它把系统指令、用户输入、对话历史、检索证据、工具结果和输出预留装配成有限 Token 预算内的请求。

## 不理解会造成什么错误

- 把全部历史和文档塞入窗口，关键证据反而被噪声淹没。
- 只在超限后从末尾硬截断，丢掉当前问题或安全规则。
- 未给输出预留 Token，模型在 JSON 或答案中途被截断。
- 把旧工具结果当成最新事实，或让不可信文档覆盖系统规则。
- 用字符数估计 Token，中文、代码和表格频繁超限。

## 它在 LLM 链路中的位置

```text
系统规则 ─┐
用户问题 ─┼→ 候选信息 → 去重与可信度标记 → 预算分配与排序
历史消息 ─┤                                      ↓
检索证据 ─┤                              最终上下文 → 模型
工具结果 ─┘
```

Prompt 定义长期任务协议，上下文工程为单次请求选择运行时信息。文档如何切分、召回和重排属于 [RAG](../K-%E6%A3%80%E7%B4%A2%E5%A2%9E%E5%BC%BA%E7%94%9F%E6%88%90%20RAG/00-%E6%A3%80%E7%B4%A2%E5%A2%9E%E5%BC%BA%E7%94%9F%E6%88%90%20RAG-MOC.md)。

## 从客服问答开始

用户问：“我昨天改过地址，订单 A102 会送到哪里？”候选上下文包括系统规则、当前问题、二十轮历史、订单工具结果和多篇配送文档。

正确装配应优先保留当前身份与问题、最新订单状态、相关政策和足够输出空间；旧闲聊和重复文档可以摘要或删除。工具结果要带时间戳，检索文档要标记为不可信内容，而不是新指令。

## 先建立简单基线

先只使用系统规则、当前用户问题和一条最相关证据，并记录正确率、Token 数和截断率。加入历史、更多检索结果或摘要前，必须证明它解决了固定失败案例。

## 上下文预算公式

设模型总窗口为 $W$，系统与固定 Prompt 为 $S$，当前用户输入为 $U$，历史为 $H$，检索证据为 $R$，工具结果为 $G$，输出预留为 $O$，安全余量为 $M$。请求必须满足：

$$
S+U+H+R+G+O+M\le W
$$

真正可分配给可选上下文的预算为：

$$
B_{optional}=W-S-U-O-M
$$

若 $B_{optional}<0$，说明连必需输入和输出预留都放不下，应拒绝、缩短任务或改用更大窗口，不能偷偷删除安全规则。

## 信息选择与排序

为候选片段 $i$ 定义效用 $v_i$、Token 成本 $t_i$、可信度 $q_i$ 和新鲜度 $f_i$。一个简单优先分数是：

$$
s_i=\frac{v_iq_if_i}{t_i}
$$

它表示单位 Token 的预期价值，但不是完整最优解。安全规则和当前问题是不可删除约束；证据选择还要避免重复、冲突和“高相似但不回答问题”的片段。

常见顺序是先放清晰任务与当前问题，再放紧邻问题的证据。不同模型对长上下文位置的利用可能不同，应在目标模型上测试，不把固定顺序当普遍定律。

## 最小手算

窗口 $W=4096$，固定 Prompt 500，用户输入 300，输出预留 800，余量 200，则可选预算：

$$
4096-500-300-800-200=2296
$$

若历史 1200、检索 1600、工具结果 400，共 3200 Token，就超出 904。应按任务价值压缩或删除可选内容，而不是侵占输出预留。

两个片段的 `(效用, 可信度, 新鲜度, Token)` 分别为 `(9,1,1,300)` 和 `(8,0.5,1,100)`，单位预算分数为 0.03 和 0.04。第二段更省预算，但可信度较低；高风险答案不能仅凭该分数选择来源。

## 可执行实验

下面的装配器先保留必需内容，再按单位预算价值选择可选片段。它同时验证正常装配和必需内容已经超限的失败分支。

```python
import random

random.seed(42)

def assemble(window, output_reserve, margin, required, optional):
    required_cost = sum(item["tokens"] for item in required)
    budget = window - output_reserve - margin - required_cost
    if budget < 0:
        raise ValueError("required context exceeds safe input budget")
    chosen = list(required)
    ranked = sorted(
        optional,
        key=lambda item: (item["value"] * item["trust"] / item["tokens"]),
        reverse=True,
    )
    for item in ranked:
        if item["tokens"] <= budget:
            chosen.append(item)
            budget -= item["tokens"]
    return chosen, budget

required = [
    {"name": "system", "tokens": 120, "value": 100, "trust": 1.0},
    {"name": "current_user", "tokens": 80, "value": 100, "trust": 0.0},
]
optional = [
    {"name": "latest_order", "tokens": 180, "value": 10, "trust": 1.0},
    {"name": "old_chat", "tokens": 250, "value": 2, "trust": 0.8},
    {"name": "duplicated_doc", "tokens": 200, "value": 3, "trust": 0.6},
]
chosen, remaining = assemble(800, 200, 50, required, optional)
names = [item["name"] for item in chosen]
assert names[:2] == ["system", "current_user"]
assert "latest_order" in names
assert sum(item["tokens"] for item in chosen) + 200 + 50 <= 800

try:
    assemble(300, 150, 50, required + [
        {"name": "mandatory_policy", "tokens": 100, "value": 100, "trust": 1.0}
    ], [])
    raise AssertionError("over-budget required context should fail")
except ValueError:
    pass

print(names, "remaining optional budget", remaining)
```

## 实验结果解释

实验保证必需内容不会被静默截断，并在预算内选择高价值片段。它使用人工 Token 数和简单贪心分数，不等价于真实 Tokenizer 计数，也不能评价证据是否事实正确。生产系统要保存最终装配快照和每段来源。

## 质量延迟与成本影响

- 输入 Token 增加会提高 Prefill 计算、传输和费用；对长上下文模型，增长可能显著影响延迟。
- 摘要能节省 Token，也会丢失细节并引入新的模型错误。
- 检索数量越多不代表回答越好，应画质量随上下文长度的曲线。
- 输出预留过大浪费窗口，过小导致答案和结构被截断，应按任务输出长度分布设定。

## 数据评测与安全风险

检索文档、网页、用户历史和工具文本都可能含提示注入。必须保留来源与可信度，隔离指令和数据，并在工具层重新授权。上下文日志可能包含个人信息、密钥和内部文档，应最小化采集、脱敏并限制保留期。

评测要覆盖证据存在、证据缺失、证据冲突、过期证据、长历史和超预算请求。不能只在“答案刚好位于开头”的样例上测长上下文能力。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 答案忽略关键证据 | 排序差或上下文噪声 | 最终装配快照、证据位置、消融 |
| 输出经常被截断 | 没有输出预留 | 输入输出 Token 分布、停止原因 |
| 多轮后规则丢失 | 从错误一端硬截断 | 必需段策略、历史摘要、窗口公式 |
| 引用过期状态 | 工具结果缺少时间 | 来源时间戳、缓存 TTL、新鲜度 |
| 成本持续增长 | 历史和文档无界累积 | 分段 Token、去重、摘要触发点 |
| 文档改变工具行为 | 上下文污染 | 信任标签、指令边界、工具授权 |

## 适用与不适用场景

上下文工程适合模型已具备能力，但缺少本次请求所需事实、状态或对话信息的场景。稳定改变输出风格可先用 Prompt；需要大量新领域行为时评估 SFT；需要外部事实检索时进入 RAG。扩大窗口不能替代相关性选择、权限控制和事实验证。

## 学习收益

你应能写出上下文预算式，区分必需和可选信息，设计超限失败策略，并评价上下文对质量、延迟、成本和安全的共同影响。

## 给别人讲清楚

“上下文不是越多越好，而是一只容量有限的工作台：当前问题、可靠证据和输出空间要先占位，旧信息和噪声按价值取舍。”

## 自检问题
