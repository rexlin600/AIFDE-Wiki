# FDE 能力模型

## 一句话定义

前沿部署工程师（Forward Deployed Engineer，FDE）以端到端交付为责任边界，在客户真实环境中连接软件、数据、AI、生产可靠性、安全、业务发现和产品复用。

## 如何使用本模型

本模型用于诊断能力与证据，不是按年限晋升的职级表。六个维度分别评估；一个人可能在软件工程达到 L4，在客户交付仍处于 L2。评级依据可核验行为，而不是“了解”“熟悉”或工具清单。

- **L1 认知：** 能解释概念、边界和基本取舍，在指导下完成局部任务。
- **L2 实验：** 能完成有验收标准的原型或最小闭环，记录过程与结果。
- **L3 工程：** 能独立负责生产可用的子系统或客户工作流，以测试和指标说明质量。
- **L4 生产/FDE：** 能在模糊、多方和高约束环境中负责端到端结果，建立可复用机制并帮助他人交付。

合格证据通常包括代码与版本、设计决策、测试或评测集、运行指标、客户验收、事故复盘、Runbook 和复用记录。保密项目只描述经过脱敏且获准公开的结构性证据。

## 维度一：软件和数据工程

这个维度关注把模型能力接入真实系统所需的代码、API、数据管道、存储、测试和调试能力。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能用 Python 编写清晰的小型服务或数据脚本；理解 HTTP、JSON、SQL、Git、测试和日志；能定位常见输入、依赖与数据类型错误。证据是可运行代码、基本单元测试和使用说明。 |
| L2 | 能设计带校验、错误处理和持久化的 API；构建可重复的数据摄取或 ETL 流程；为边界条件编写集成测试。证据是版本化仓库、数据契约、测试报告和可复现命令。 |
| L3 | 能负责生产子系统，处理异步任务、并发、幂等、迁移、性能和可观测性；能集成企业 API、身份和数据平台。证据是架构决策、负载测试、SLO、告警和故障处置记录。 |
| L4 | 能在遗留系统、云与本地混合环境中定义技术边界和演进方案；主导跨团队数据契约、可靠性标准和复杂故障诊断，并沉淀平台组件。证据是多系统上线、长期运行指标、迁移或事故复盘及跨项目复用。 |

## 维度二：AI/LLM 应用工程

这个维度关注模型选型、Prompt 与 Context、RAG、Agent、评测及其与产品工作流的组合，而非只会调用 API。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能解释 Token、上下文窗口、结构化输出、Embedding、RAG 与 Agent 的用途和局限；能完成受控的模型调用。证据是最小示例、失败样例和成本估算。 |
| L2 | 能实现 RAG 或工具调用原型，建立小型评测集，比较 Prompt、模型或检索配置。证据是固定数据集、实验变量、质量/延迟/成本结果和错误分类。 |
| L3 | 能设计生产级 LLM 工作流，处理权限、引用、状态、重试、Fallback 和回归评测；能在 RAG、长上下文、工具与微调之间作取舍。证据是端到端评测、Trace、上线门禁和架构决策。 |
| L4 | 能把模糊业务流程转化为可评测 AI 系统，识别能力边界并调整产品流程；主导复杂 Agent/RAG 系统优化和跨场景方法复用。证据是业务指标改善、持续评测、重大失败分析与通用框架。 |

## 维度三：生产可靠性与安全

这个维度关注系统在延迟、成本、可用性、隐私、权限和攻击条件下能否持续、负责地运行。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能识别超时、限流、密钥、PII、Prompt Injection 和幻觉等基本风险；不会在日志或仓库中泄露秘密。证据是风险清单和安全配置。 |
| L2 | 能加入超时、重试、限流、缓存、输入输出校验、基础监控和人工兜底；能执行威胁建模和故障演练。证据是仪表盘、测试用例、运行手册和演练记录。 |
| L3 | 能定义 SLO、容量与成本预算，建立 Trace、回归评测、分阶段发布、回滚、最小权限和审计；能主持生产事故处置。证据是 SLO 报告、安全评测、变更记录和无责复盘。 |
| L4 | 能在受监管或多租户环境中协调安全、法务、平台和客户团队，决定数据驻留、隔离、治理及风险接受边界；把事件经验转为组织级控制。证据是审计材料、风险签署、跨项目控制和持续改进指标。 |

## 维度四：需求发现与业务建模

这个维度关注从模糊诉求识别真实用户、现有流程、约束、价值和可验证成功标准。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能区分用户请求、问题和解决方案；在访谈中记录参与者、输入输出、痛点与假设。证据是问题陈述、流程草图和待验证假设。 |
| L2 | 能主持范围明确的 Discovery，把流程拆为决策点和异常路径，定义基线、验收标准与 PoC 边界。证据是流程模型、指标定义、样本数据和验收清单。 |
| L3 | 能在数据不足和利益冲突下量化价值、风险与 ROI；通过原型发现需求错误，并据证据调整范围。证据是优先级决策、实验结论、业务案例和签署的上线条件。 |
| L4 | 能重构跨团队业务流程而非机械自动化旧流程；识别组织、合规和采用阻力，建立分阶段价值路线。证据是持续业务结果、决策记录、采用数据与高层对齐材料。 |

## 维度五：客户沟通与交付

这个维度关注与客户工程师、业务负责人、安全团队和管理者共同推进结果，并在变化与故障中维持信任。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能用受众理解的语言解释技术状态，明确记录行动项、负责人和期限；能诚实表达未知与风险。证据是会议纪要、演示脚本和清晰的书面更新。 |
| L2 | 能独立演示原型、收集结构化反馈、管理小范围交付计划并及时升级阻塞。证据是演示反馈、风险日志、验收记录和状态报告。 |
| L3 | 能协调客户与内部多团队，处理需求变化、上线决策和生产故障；把技术权衡转译为业务影响。证据是联合计划、决策日志、事故沟通和正式交接。 |
| L4 | 能在高模糊或高压力项目中建立可信合作机制，推动高层决策、谈判范围并培养客户团队自主运营。证据是复杂项目成果、利益相关者反馈、采用率和交付方法论。 |

## 维度六：产品化与复用

这个维度关注从一次性交付中识别稳定抽象，使后续客户更快、更安全地获得价值，同时避免过早平台化。

| 等级 | 可观察行为证据 |
| --- | --- |
| L1 | 能区分客户专用配置与可复用代码，保持模块边界和基本文档。证据是清晰目录、配置说明和重复点清单。 |
| L2 | 能把重复的连接器、Prompt、评测或部署步骤提取为有测试的组件。证据是组件接口、版本、测试和第二个场景的使用记录。 |
| L3 | 能基于多个交付识别稳定产品能力，定义扩展点、兼容策略、维护责任和采用指标。证据是路线决策、迁移指南、发布记录和复用率。 |
| L4 | 能平衡客户时效与平台演进，把前线信号转化为产品优先级；推动跨团队标准并淘汰脆弱的定制分支。证据是跨客户平台能力、交付周期下降、质量提升和组合层面的取舍记录。 |

## 综合评估与成长计划

评估时为每个维度选择“已经反复证明”的最高等级，并附最多三项强证据和一个主要缺口。不要取六维平均值掩盖短板：例如面向受监管客户的 Agent 项目，即使 AI 应用能力达到 L3，可靠性与安全停留在 L1 也不具备独立上线条件。

建议每个成长周期只选择一到两个证据目标：

1. 选择一个真实工作流和可量化基线；
2. 明确希望提升的维度与目标等级；
3. 在项目开始前定义可公开或可脱敏的证据；
4. 用评测、运行和客户反馈验证结果；
5. 复盘失败，并把可复用结论更新到知识库。

## 常见误区

- **把 FDE 当成驻场开发：** 工作地点不是能力定义，核心是对结果、集成和采用负责。
- **用 Demo 代替交付：** Demo 证明可能性，交付还需要数据、评测、安全、可靠性和交接证据。
- **只评 AI 技术深度：** 客户沟通、需求建模和生产运行是独立维度，不会由模型知识自动补齐。
- **把所有定制都产品化：** 单一客户需求未必代表稳定抽象，应等待第二个真实场景验证。
- **按工具清单定级：** 使用过某框架不等于能解释边界、处理失败并对业务结果负责。
