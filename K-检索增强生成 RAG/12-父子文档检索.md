# 父子文档检索

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 RAG 问题

小片段更容易与查询精确匹配，却常缺少解释所需的上下文；大片段语义完整，却可能被无关文字稀释。父子文档检索用“小块召回、大块生成”分离这两个粒度：索引子块，命中后按映射取回所属父块。

## 不理解会造成什么错误

- 命中一句限制条件，却没返回同节中的适用对象。
- 把整章直接做 Embedding，标题和大量无关段落稀释相似度。
- 多个子块都命中同一父块时重复塞入上下文。
- 子块更新后仍指向旧父版本，引用内容与召回内容不一致。
- 先取父块再做权限过滤，暴露同一文档中的受限内容。

## 它在 RAG 链路中的位置

```text
父文档 → 切成子块 → 子块索引
查询 → 召回子块 ID → 权限校验 → parent_id 去重 → 读取父块 → 重排与装配
```

它改变的是召回结果到生成上下文之间的映射，不替代 [RAG 文档切分](06-RAG%20文档切分.md)、检索器或权限控制。

## 从员工报销问答开始

用户问“上海出差住宿每天上限是多少？”子块“上海：600 元/晚”很容易召回，但答案还需要父节里的“仅适用于 P1 至 P3 员工”和“含税”条件。系统用子块定位，再返回完整的“国内住宿标准”父节。

简单基线是直接把同一种 Chunk 同时用于检索和生成。先测其 Recall、答案支持率和上下文 Token，再判断是否真的需要两级粒度。

## 输入输出与映射状态

每个子块至少保存：`child_id`、`parent_id`、文本、版本、权限标签和位置。父块保存 `parent_id`、完整文本、来源与同一版本。查询输出不是“若干子块文本”，而是：

```text
[(child_id, child_score)] → [(parent_id, aggregate_score, matched_children)]
```

版本应参与映射键，例如 `(document_id, version, parent_id)`，避免新版子块读取旧版父块。

## 父块怎样聚合得分

父块 $p$ 下命中的子块集合记为 $C_p$，子块分数为 $s_c$。最简单方法取最大值：

$$
S(p)=\max_{c\in C_p}s_c
$$

它表示“父块中最匹配的一处有多相关”。若直接求和，切得更碎的父块会因命中数量多而占便宜。也可使用带衰减的前几名：

$$
S(p)=s_{(1)}+\lambda s_{(2)},\quad 0\le\lambda<1
$$

其中 $s_{(1)}\ge s_{(2)}$。无论用哪种规则，都要在固定评测集验证，而不是把聚合分数当概率。

## 最小手算

父块 A 的两个子块得分为 0.82 和 0.60，父块 B 的一个子块为 0.78。最大值聚合得到 A=0.82、B=0.78，A 在前。若直接求和，A=1.42，这个数主要反映命中数量，无法与 B 公平比较。

若每个子块 80 Token、父块 300 Token，三个命中都属于 A。错误实现会放入 900 Token 的重复父块；按 `parent_id` 去重后只放 300 Token。

## 可执行实验

```python
children = [
    {"id": "a1", "parent": "A", "version": 2,
     "score": 0.82, "acl": {"staff"}},
    {"id": "a2", "parent": "A", "version": 2,
     "score": 0.60, "acl": {"staff"}},
    {"id": "b1", "parent": "B", "version": 2,
     "score": 0.78, "acl": {"finance"}},
]
parent_metadata = {
    "A": {"version": 2, "acl": {"staff"}},
    "B": {"version": 2, "acl": {"finance"}},
}
parent_text = {
    "A": "上海住宿上限 600 元，适用于 P1 至 P3，含税。",
    "B": "财务内部预算。",
}
text_reads = []

def authorized_parent_read(parent_id, child_version, role):
    metadata = parent_metadata.get(parent_id)
    if (not metadata or role not in metadata["acl"]
            or child_version != metadata["version"]):
        return None
    # 只有元数据授权通过后，存储接口才读取正文。
    text_reads.append(parent_id)
    return {**metadata, "text": parent_text[parent_id]}

def retrieve_parents(role, items=children, limit=2):
    allowed = []
    for child in items:
        if role not in child["acl"]:
            continue
        parent = authorized_parent_read(child["parent"], child["version"], role)
        if parent:
            allowed.append({**child, "parent_record": parent})
    scores = {}
    matches = {}
    for child in allowed:
        pid = child["parent"]
        scores[pid] = max(scores.get(pid, float("-inf")), child["score"])
        matches.setdefault(pid, []).append(child["id"])
    ranked = sorted(scores, key=scores.get, reverse=True)[:limit]
    return [
        {"parent": pid, "score": scores[pid], "children": matches[pid],
         "version": next(c["parent_record"]["version"] for c in allowed
                         if c["parent"] == pid),
         "text": next(c["parent_record"]["text"] for c in allowed
                      if c["parent"] == pid)}
        for pid in ranked
    ]

result = retrieve_parents("staff")
assert [x["parent"] for x in result] == ["A"]
assert result[0]["children"] == ["a1", "a2"]
assert "P1 至 P3" in result[0]["text"]
assert all(x["parent"] != "B" for x in result)  # 权限过滤早于父块读取

missing_parent = [{"id": "x", "parent": "OLD", "version": 1,
                   "score": 1.0, "acl": {"staff"}}]
stale_child = [{"id": "x", "parent": "A", "version": 1,
                "score": 1.0, "acl": {"staff"}}]
parent_denied = [{"id": "x", "parent": "B", "version": 2,
                  "score": 1.0, "acl": {"staff"}}]
assert retrieve_parents("staff", missing_parent) == []
assert retrieve_parents("staff", stale_child) == []
assert retrieve_parents("staff", parent_denied) == []
assert "B" not in text_reads

print(result)
```

## 实验结果解释

两个命中子块被聚合成一个父块，父节补齐适用条件。父元数据与正文分离，存储接口只有在子 ACL、父 ACL、父记录和版本都通过后才读取正文；断言确认父 B 正文从未读取。实验不证明人工分数来自真实向量模型，也不证明 300 Token 是最佳父块大小。

## 质量延迟与成本影响

- 更完整的父块可能提高答案支持率，也会增加输入 Token 和 Prefill 延迟。
- 父块读取多一次存储访问，可批量读取并缓存；缓存键必须含版本和权限域。
- 父块太大重新引入噪声，太小则仍缺上下文，应联合评测召回与回答。
- 一个查询命中许多父块时要限制父块数和总 Token，不能只限制子块 top-k。

## 数据评测与安全风险

按问题切片比较“子块是否召回”“正确父块是否返回”“答案是否由父块支持”。数据更新、删除和权限变化必须同时传播到子索引与父存储。文档中的指令只是证据数据，不得覆盖系统指令；日志避免记录无关父块中的个人信息。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 命中准确但回答缺条件 | 父块边界过小 | 父节内容、标题路径、错误样例 |
| 上下文大量重复 | 未按父 ID 去重 | 命中子块到父块映射 |
| 大文档总排在前面 | 子块分数直接求和 | 聚合公式、每父块命中数 |
| 引用与命中文本不一致 | 父子版本错配 | 映射键、索引版本、删除传播 |
| 出现越权段落 | 读取后才过滤 | 子块 ACL、父块 ACL、缓存键 |

## 适用与不适用场景

适合细节定位要求高、回答又依赖同节上下文的制度、合同和技术文档。不适合每条记录本身已完整的 FAQ，也不适合父块内部权限不同却无法细粒度过滤的材料。

## 学习收益

你应能区分检索粒度与生成粒度，设计稳定父子映射，解释最大值聚合和去重，并把权限与版本放在读取边界前。

## 给别人讲清楚

“先用小片段找准地址，再把它所属的完整段落拿回来；搜索用放大镜，回答用完整页面。”
