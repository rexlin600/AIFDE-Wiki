# 多轮对话检索

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么 RAG 问题

对话中的后续问题常省略实体：“它支持多久？”只有结合本会话最近明确提到的 X2，才能改写为可独立检索的查询。多轮对话检索负责指代消解和必要历史选择，同时隔离其他会话与用户。

## 不理解会造成什么错误

- 只检索“它支持多久”，完全没有产品信息。
- 把整段历史拼入查询，旧实体和闲聊污染召回。
- 从另一个会话或用户取最近实体，造成数据泄露。
- 用户明确换成 Y3 后仍沿用 X2。
- 历史不足时猜测指代对象，而不是请求澄清。

## 它在 RAG 链路中的位置

```text
当前消息 + 当前会话授权历史 → 指代与约束解析 → 独立查询
→ 检索 → 证据 → 回答 → 写入本会话状态
                  └→ 无法消解时澄清
```

它不等于把所有聊天记录塞给模型；历史选择属于请求状态管理，[RAG 上下文构建](35-RAG%20上下文构建.md)再决定哪些证据进入窗口。

## 从连续产品咨询开始

用户先问“X2 的保修政策是什么？”，再问“它在中国支持多久？”系统应得到独立查询“X2 在中国支持多久”。简单基线是只检索当前消息；只有含指代的切片明显失败时，再加入受控历史解析。

## 输入输出与会话状态

状态键至少为 `(tenant_id, user_id, session_id)`，内容包含最近确认实体、时间、权限域和来源消息 ID。输出包含独立查询、继承约束、使用了哪些历史消息、置信度与 `clarify` 标志。

## 历史选择与衰减

候选历史消息 $i$ 的简化分数可写为：

$$
s_i=r_i\exp(-\lambda\Delta t_i)
$$

$r_i$ 是与当前问题的相关性，$\Delta t_i$ 是距离当前的轮数，$\lambda$ 控制旧信息衰减。显式的新实体应覆盖旧实体；分数不能越过会话与权限硬边界。

## 最小手算

当前轮前，X2 在 1 轮前，相关性 1；Y3 在 5 轮前，相关性 0.8。取 $\lambda=0.2$，X2 分数约 $1e^{-0.2}=0.819$，Y3 约 $0.8e^{-1}=0.294$。若当前消息明确说“改问 Y3”，规则应直接选 Y3，而非依赖衰减分数。

## 可执行实验

```python
import re

ENTITY = re.compile(r"\b[A-Z]\d+\b")

class SessionStore:
    def __init__(self):
        self.state = {}

    def add(self, tenant, user, session, text):
        found = ENTITY.findall(text)
        if found:
            self.state[(tenant, user, session)] = found[-1]

    def standalone(self, tenant, user, session, text):
        explicit = ENTITY.findall(text)
        if explicit:
            return text, "explicit"
        if "它" in text or "这个产品" in text:
            entity = self.state.get((tenant, user, session))
            if entity is None:
                raise LookupError("referent missing; ask for clarification")
            return text.replace("这个产品", entity).replace("它", entity), "resolved"
        return text, "unchanged"

store = SessionStore()
store.add("t1", "u1", "s1", "请介绍 X2")
store.add("t1", "u1", "s2", "请介绍 Y3")
query, mode = store.standalone("t1", "u1", "s1", "它在中国支持多久")
assert query == "X2在中国支持多久" and mode == "resolved"

# 当前消息显式换实体时不能继承旧实体。
explicit, mode2 = store.standalone("t1", "u1", "s1", "Y3 支持多久")
assert explicit == "Y3 支持多久" and mode2 == "explicit"

try:
    store.standalone("t1", "u2", "s1", "它支持多久")
    raise AssertionError("cross-user history should not resolve")
except LookupError:
    pass

assert store.state[("t1", "u1", "s1")] == "X2"
assert store.state[("t1", "u1", "s2")] == "Y3"
print(query, explicit, "session isolation passed")
```

## 实验结果解释

同一用户的两个会话分别保留 X2 和 Y3，后续指代只使用当前会话；新用户没有历史时明确失败。正则实验不理解自然语言中的多个实体、否定作用域和长期记忆，真实系统需要置信阈值、澄清与端到端评测。

## 质量延迟与成本影响

- 受控改写提高指代查询召回，但多一次模型调用会增加延迟和 Token。
- 保存短结构化状态通常比每轮携带完整历史更省成本。
- 摘要可压缩历史，也可能改错实体与否定，需要版本和来源。
- 会话状态缓存要设置容量、过期和用户注销后的删除策略。

## 数据评测与安全风险

测试指代、实体切换、多实体、长间隔、无历史、跨会话与跨租户攻击。指标包含消解准确率、澄清率、检索 Recall、最终答案与泄露率。历史属于用户数据；授权变化和删除请求必须传播到状态、缓存、日志和离线评测副本。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| “它”检索不到结果 | 未生成独立查询 | 改写日志、最近确认实体 |
| 回答仍围绕旧产品 | 未识别显式实体切换 | 当前消息实体、覆盖规则 |
| 不同会话相互污染 | 状态键缺少 session | 租户用户会话复合键 |
| 偶发泄露其他用户内容 | 共享缓存键不完整 | 身份域、缓存、追踪日志 |
| 历史不足仍给确定答案 | 缺澄清分支 | 置信阈值、referent missing |

## 适用与不适用场景

适合连续客服、知识问答和分析助手。不适合没有认证边界的共享终端长期记忆，也不应为单轮精确查询无条件引入历史。

## 学习收益

你应能构造独立查询，处理实体切换与缺失澄清，用复合键隔离状态，并解释为什么完整历史不等于更好的检索。

## 给别人讲清楚

“对话检索像记住本次谈话中的代词，但记忆本上必须写清租户、用户和会话；认不出‘它’就问，不能翻别人的本子。”
