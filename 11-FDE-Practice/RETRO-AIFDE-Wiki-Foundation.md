# AIFDE Wiki 基础建设设计阶段复盘

## 范围

本复盘覆盖 2026-09-09 的 AIFDE Wiki 设计与本地基础建设阶段：从中文设计定稿，到仓库工具、Obsidian 配置、九类模板、指南、路线、领域 MOC 和首批证据型样例落地。它不复盘尚未发生的 GitHub 公开发布、外部实验运行或读者采用效果。

## 目标与结果

已确认的目标是建立一个“以 Obsidian 编辑、以 GitHub 公开阅读为优先”的中文 AI/FDE 知识库基础版本，用稳定领域目录、MOC、阶段路线和九类笔记连接概念学习与可核验证据。

截至本复盘：

- 已形成中文设计文档与分任务实施计划。
- 已建立目录、Properties 枚举、九类模板、Python 校验器与 Markdown lint 配置。
- 已建立七阶段路线、十个领域 MOC，以及项目、开源、面试和岗位样例。
- 本轮新增 concept、pattern、experiment、decision 和 retrospective 五类样例，其中实验明确停留在设计状态。
- 尚未创建或确认公开远程仓库，未执行首次远程发布，也没有真实读者反馈或外部实验结果。

因此，本地信息架构与内容模型已有可审查实例，但“公开可用”和“被目标读者采用”仍不能宣称完成。

## 做得好的地方

- **先固定证据边界**：设计明确禁止虚构仓库、Commit、Release、岗位内容和实验结果；项目与实验档案在证据缺失时保持 `draft` 或空字段。
- **让公开阅读约束编辑方式**：GitHub 兼容的相对 Markdown 链接被设为统一格式，Obsidian 只作为增强编辑器。
- **用模板验证信息架构**：九类文档不是停留在枚举定义，而是逐步补齐真实样例，能暴露字段和章节是否足够表达证据。
- **把广度与深度分开**：MOC 用 `core`、`common`、`extension` 和 L1～L4 标记范围，避免把主题清单误当作全部都要同深度完成。
- **中文化修订有独立记录**：提交 `25a05fc` 将设计文档主体翻译并统一为中文，符合“中文为主、关键术语保留英文”的目标。

## 失败与根因

### GitHub 与 Wiki Link 的兼容性冲突

早期设计需要同时服务 Obsidian 编辑和 GitHub 阅读。若采用 `[[Wiki Link]]`，作者输入更短，但公开渲染、静态校验和重名解析会依赖宿主；若两种格式并存，规则和迁移成本会上升。根因不是某个编辑器配置错误，而是“本地知识管理语法”与“通用公开 Markdown”优化目标不同。

处理结果是明确选择标准相对 Markdown 链接，并将 Obsidian 的 `useMarkdownLinks` 设为 `true`。详细权衡记录在 [ADR-001](../09-Production-AI/ADR-001-Wiki-Link-Format.md)。

### 设计语言曾与目标读者不一致

仓库目标是中文知识产品，但设计文档经历了中文化修订。根因是设计表达与成品语言规范没有在最初文本中完全对齐。修订解决了当前文档问题；后续需要在评审清单中更早检查正文语言与术语首次出现规则。

### 公开发布仍未闭环

本地仓库当前没有已确认的 Git 远程地址，项目档案的 `github`、实验的 `repository` 和 `commit` 因而保持为空。根因是远程 Owner、仓库地址和公开发布属于需要仓库所有者确认的独立动作，不在本地基础建设的授权范围内。这是已知未完成项，不应以示例 URL 或虚假哈希掩盖。

表中的负责人是角色而非个人姓名；远程发布和实验的准确日期应由相应负责人确认，不在本复盘中猜测。

## 可复用经验

- 公开知识库先选最低阅读基线，再选择编辑器增强；否则作者便利可能制造读者锁定。
- “未运行”“未发布”和空证据字段是有效状态，比看似完整但不可核验的样例更诚实。
- 模板只有被不同类型的真实内容填过，才能验证字段是否足够、边界是否清晰。
- 路线、MOC 与实验要共享相同的证据语言：目标、实际结果和下一步必须分开。
- 中文化不是机械翻译；固定英文术语、文件名和命令应保留，解释与导航则以目标读者语言为主。
