# 自定义算子与模型编译

<!-- markdownlint-disable MD012 MD013 -->

## 它解决什么深度学习问题

现成 PyTorch 算子无法表达特殊计算，或 Python 与内存访问成为性能瓶颈时，才需要自定义梯度、算子融合和模型编译。目标是保持数学语义正确的前提下扩展能力或减少运行开销。

## 不理解会造成什么错误

- 自定义 `backward` 形状正确但数值错误，模型静默学偏。
- 原地修改反向所需张量，破坏 Autograd 版本检查。
- 只测一次编译运行，把编译成本当成稳态性能。
- 为追求图完整而删除必要控制流，改变模型语义。

## 它在训练系统中的位置

这是建立正确 eager 模型、完整测试和性能剖析之后的扩展层。自定义 Autograd 负责“梯度怎么算”，`torch.compile` 负责“怎样捕获并优化一串计算”，二者解决不同问题。

## 从特殊激活开始

假设需要立方激活 $y=x^3$。PyTorch 原生运算已能自动求导，本不需要自定义算子；这里故意手写只是学习接口。真实项目只有在调用外部库、实现特殊梯度或融合内核时才承担这项维护成本。

## 自定义 Autograd 的契约

前向：

$$
y_i=x_i^3
$$

导数：

$$
\frac{\partial y_i}{\partial x_j}=
\begin{cases}
3x_i^2,&i=j\\
0,&i\ne j
\end{cases}
$$

反向接收上游梯度 $g_i=\partial L/\partial y_i$。由链式法则：

$$
\frac{\partial L}{\partial x_i}=g_i\frac{\partial y_i}{\partial x_i}
=3g_ix_i^2
$$

因此 `backward` 不是只返回局部导数 $3x^2$，而要乘上游梯度。返回值数量必须与 `forward` 输入参数数量匹配。

## 最小手算

$x=2$ 时 $y=8$。若后续损失 $L=5y$，上游梯度是 5，所以 $dL/dx=5\times3\times2^2=60$。只返回 12 会漏掉后续计算对梯度的影响。

## NumPy 有限差分

```python
import numpy as np

x = np.array([2.0, -1.5])
analytic = 3 * x ** 2
epsilon = 1e-6
numeric = ((x + epsilon) ** 3 - (x - epsilon) ** 3) / (2 * epsilon)
print("analytic", analytic)
print("numeric", np.round(numeric, 8))
print("max error", np.max(np.abs(analytic - numeric)))
```

中心差分用函数值近似导数。步长过大有截断误差，过小有浮点舍入误差，因此通过并不构成数学证明，但能发现大量实现错误。

## PyTorch 梯度与编译实验

```python
import torch

class Cube(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x ** 3

    @staticmethod
    def backward(ctx, grad_output):
        (x,) = ctx.saved_tensors
        return grad_output * 3 * x ** 2

torch.manual_seed(42)
x = torch.randn(4, dtype=torch.double, requires_grad=True)
print("gradcheck", torch.autograd.gradcheck(Cube.apply, (x,)))

def block(tensor):
    return torch.relu(Cube.apply(tensor) + 1)

eager = block(x.detach().float())
if not hasattr(torch, "compile"):
    print("compile unavailable: torch.compile is not present")
else:
    try:
        compiled = torch.compile(block, backend="eager")
        actual = compiled(x.detach().float())
        torch.testing.assert_close(actual, eager)
        print("compile semantics match", tuple(actual.shape))
    except (RuntimeError, AttributeError, ImportError) as error:
        print("compile unavailable in this runtime:", str(error).splitlines()[0])
```

`backend="eager"` 检查图捕获和语义，不代表获得性能加速。部分 PyTorch 与 Python 版本组合不支持 Dynamo，示例会明确跳过；真实基准应使用受支持的目标后端、预热、多次测量和同步设备。

## 模型编译在做什么

`torch.compile` 尝试捕获 Python 帧中的张量计算，生成可优化图并缓存。算子融合可减少中间张量读写和内核启动。输入形状、类型或控制条件不满足已有 guard 时可能重新编译；无法捕获的部分会产生图中断或回退到 eager。

## 如何做可信性能实验

1. 先用 profiler 确认瓶颈，不凭直觉重写；
2. 验证 eager 与编译输出和梯度在容差内一致；
3. 排除首次编译时间，预热后测多轮中位数；
4. GPU 计时时在边界同步，否则只测到异步提交；
5. 同时记录吞吐、峰值内存、编译时间和输入形状；
6. 将模型更新或动态形状导致的重编译纳入长期成本。

## 实验结果解释

`gradcheck=True` 表明当前双精度输入附近，解析梯度与数值梯度一致，不覆盖所有输入和边界。编译输出一致只证明语义样例，不证明更快。小模型可能因调用和编译开销反而变慢。

## 训练与推理差异

训练编译还需捕获或生成反向图，保存中间状态，并兼容优化器和分布式同步；推理图没有梯度，通常更简单。训练与推理应分别建立正确性测试和性能基准。

## 数据与验证风险

性能测试输入必须代表生产形状分布，不能只用最容易编译的固定形状。自定义算子要覆盖空张量、非连续张量、不同类型、设备和极值；无法支持的范围应显式拒绝。

## 工程排错

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| gradcheck 失败 | 漏乘上游梯度或精度不足 | 手推导数、double、epsilon、形状 |
| 反向报原地修改 | 保存张量版本变化 | 原地算子、clone、异常检测 |
| 编译频繁发生 | 输入或控制流触发 guard | 重编译日志、形状、Python 分支 |
| 编译后更慢 | 模型太小或图中断多 | 预热、profiler、完整图比例 |
| 输出仅有微小差异 | 运算顺序或融合改变 | dtype、容差、误差是否累积 |

## 适用与不适用场景

只有 profiler 指向明确热点，或现有算子无法表达正确语义时才自定义。现有 PyTorch 组合算子能满足需求时，优先使用它们。编译适合重复运行且图较稳定的工作负载，不保证每个模型或硬件都加速。

## 学习收益

你应能从局部导数推到向量雅可比积，编写并检查自定义 Autograd，解释图捕获、guard、图中断和融合，并设计不夸大加速的基准。

## 给别人讲清楚

“自定义算子是在告诉框架这一步怎样算、梯度怎样传；模型编译则把许多正确步骤组织成更高效的执行计划。正确性永远先于速度。”
